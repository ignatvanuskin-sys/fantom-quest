# Fantom — сайт хоррор-квеста и система бронирования

Production-ready сайт квеста Fantom (QuestHouse Fantom & KinoLand, Усть-Каменогорск) с
серверным рендером, REST API бронирования, админ-панелью и audit log.

Проект **не имеет внешних зависимостей**: только Node.js ≥ 18.17. Это сделано осознанно —
развёртывание сводится к копированию папки и одной команде, без `npm install` и без риска
сломать сборку обновлением транзитивной зависимости.

---

## 1. Быстрый старт

```bash
node src/seed.js --reset    # создать базу из исходных данных
npm start                   # http://localhost:3000
npm test                    # 59 тестов: API, слоты, ночной график, админка, SEO
```

Админка: `http://localhost:3000/admin` · токен по умолчанию `dev-admin-token-change-me`
(обязательно замените, см. раздел 4).

### Скрипты

| Команда | Что делает |
|---|---|
| `npm start` | Запуск сервера |
| `npm run dev` | Запуск с автоперезапуском (`node --watch`) |
| `npm run seed` | Пересоздать `data/db.json` из исходных данных |
| `npm run seed:dry` | Показать, что будет создано, без записи |
| `npm test` | Полный прогон тестов на изолированной базе |

и `/healthz` для оператора. Посетитель видит только рабочий сайт.

### Правило достоверности

Бриф запрещает выдумывать цены, сценарии, возраст, состав команды, уровни контакта,
предоплату, фото, отзывы и свободные слоты. Это правило встроено в архитектуру:

* всё, что не подтверждено публичными источниками, лежит в `src/seed-data.js` со значением
  `null` и флагом `confirmed: false`, и попадает в `settings.unconfirmedFields`;
* интерфейс печатает такие значения компонентом `unconfirmed()` — плашкой
  «Уточняется» / «Нужно подтвердить» — и никогда не подставляет выдуманное число;
* в Schema.org **не выводятся** `priceRange`, `offers` и `aggregateRating`
  (агрегированный рейтинг 2ГИС — не собственные отзывы бизнеса). `Review` размечается
  только для отзывов с подтверждённым источником;
* фотографии не заменяются стоковым хоррором: в разметке стоят именованные слоты
  с требованиями (`IMAGE_REQUIREMENTS`), а визуальный язык построен на процедурных
  текстурах (SVG-зерно, градиенты бетона) — они не выдают себя за кадры бизнеса.

### Запись: цена и число гостей

Стартовое число гостей в мастере берётся из выбранной программы (`baseGuests`), а не из
константы: у «Пакет Хоррор» это 2 человека, у программ Level — 6. Раньше в форме стояло
жёсткое «4» при цене «2 человека — 17 500 ₸», и сводка противоречила сама себе.

Число гостей живёт на шаге контактов, а не на отдельном шаге: одно поле не стоило отдельного
экрана. Всего шагов пять.

При выборе Telegram появляется поле для ника — без него администратору некуда написать.
Ник нормализуется до вида `@username` (и на клиенте, и на сервере), проверяется по формату
Telegram и хранится только для Telegram: у WhatsApp и звонка адрес известен из телефона,
и спрашивать там ник было бы лишним. В админке ник выводится ссылкой на чат.

Рядом с ценой выводится прайс-лист программы (`priceNote`): сколько человек включено и
сколько стоит каждый следующий. **Итог по числу гостей не считается автоматически** —
у «Пакет Хоррор» тариф «от 4 человек» означает умножение на всех гостей, а у Level mini
доплата идёт только с седьмого. Одинаковые на вид поля `tiers` описывают разные правила,
поэтому авторасчёт ждёт подтверждения владельца (см. `AUDIT.md`).

### Схема данных

Сущности брифа и их поля:

**Quest** — `id, slug, name, brandLabel, genre, shortDescription, longDescription,
durationMinutes, locationId, isPrimary, isPlaceholder, active, bookingEnabled, intensity,
ageLimit, minGuests, maxGuests, priceFrom, priceNote, contactLevel, stopWord, suitedFor,
heroImage, gallery, imageRequirements, sources, unconfirmed[]` + флаги `*Confirmed`.

**Location** — `id, name, city, region, country, streetAddress, floor, postalCode,
fullAddress, landmark, lat, lng, mapUrl, routeUrl, entranceNote, entranceConfirmed, source`.

**AvailabilitySlot** — `id (slot_YYYY-MM-DD_HHMM), businessDate, time, startIso, endIso,
capacity, booked, status, questId, bookingId, note, updatedAt`.
Статусы: `open | held | booked | blocked | past | unavailable`.
Базовая сетка считается из расписания; в `db.slots` хранятся только слоты, состояние
которых отличается от «свободен» (закрытые администратором и занятые заявками).

**Booking** — `id, reference, questId, questName, locationId, date, businessDate, startTime,
endTime, startIso, endIso, timezone, durationMinutes, guests, name, phone, messenger,
messengerLabel, comment, price, priceStatus, source, userAgent, consentAt, status, createdAt,
updatedAt, history[]`.
Статусы: `new, pending_confirmation, confirmed, moved, cancelled, completed, no_show`.

**Customer** — `id, name, phone, messenger, bookings[], createdAt, updatedAt, consent`.
Хранится минимум персональных данных: имя, телефон, канал связи, комментарий, факт согласия.

**Review** — `id, author, rating, text, publishedAt, sourceLabel, sourceUrl, verified,
status, placeholder, order`. Публикуется только при `verified: true` и наличии `sourceUrl`.

**FAQ** — `id, question, answer, status, confirmed, placeholder, source, order`.
`status: published` только при заполненном ответе; иначе `needs_confirmation`.

**SiteSettings** — `brand, city, country, timezone, locale, phone, whatsappUrl, instagramUrl,
hours, rating, payments, notificationChannel, mockModeBanner, unconfirmedFields, seo`.

## 5. Уведомления и ручное подтверждение

**MVP.** После успешной записи заявка получает статус `new` и слот помечается `held`.
Администратору уходит уведомление; в ответе API и на экране успеха клиент получает
**готовый deep link WhatsApp** с подставленным текстом подтверждения.

```
[notify] каналы: Telegram → webhook → e-mail (первый настроенный побеждает по факту доставки)
[notify] WhatsApp — только вручную, через deep link
```

**Автоматическая отправка в WhatsApp намеренно не реализована.** Она требует
WhatsApp Business API / Twilio / 360dialog с верифицированным отправителем; без credentials
это обещание, которое нельзя выполнить. Вместо этого — deep link и ручное подтверждение,
как и требует бриф.

### MOCK_MODE

По умолчанию `MOCK_MODE=true`. В этом режиме:

* заявки сохраняются в базу и audit log;
* **реальному бизнесу ничего не отправляется**;
* в публичном интерфейсе режим **не показывается вообще** — сайт выглядит и работает как обычный;
* диагностика доступна оператору: `GET /healthz` → `notifications.mockMode`, и статус виден в админке.

Это защита от того, чтобы тестовые заявки не попали администратору квеста. Осознанное
решение: посетитель не должен читать технические подробности стенда — он должен записаться.
Строку «Тестовый режим» на страницах убрали, чтобы сайт нельзя было принять за нерабочий;
вместо этого состояние видно оператору там, где он его ищет.

### Ручной процесс подтверждения

1. Заявка → статус `new`, слот `held`.
2. Администратор открывает `/admin` → «Заявки», нажимает WhatsApp (ссылка уже с текстом).
3. Подтвердил → статус `confirmed`, слот `booked`.
4. Не дозвонился → `cancelled` (слот освобождается) или перенос → `moved`.
5. После игры → `completed`. Не пришли → `no_show` (слот освобождается).

### V2 (не входит в MVP)

WhatsApp Business API, синхронизация с Google Calendar / Cal.com, напоминания за 24 и 3 часа,
автоматический follow-up после визита, webhook в CRM, периодическое удаление устаревших
персональных данных.

## 6. Ночной график (ключевая деталь)

Смена 09:00–02:00 пересекает календарную дату. Слот «01:00» относится к **предыдущему**
игровому дню, поэтому слот хранится парой `(businessDate, time)`, где `businessDate` — дата
открытия смены. Абсолютное время считается в `src/lib/time.js`:

```
businessDate = 2026-10-05, time = 01:00  →  2026-10-05T20:00:00Z  (06.10 01:00 UTC+5)
businessDate = 2026-10-05, time = 09:00  →  2026-10-05T04:00:00Z
```

Игровое окно: `[D 09:00, D+1 02:00)`. Игра длится 60 минут, поэтому последний старт — 01:00
(оканчивается ровно в 02:00). В интерфейсе ночные слоты помечены «после полуночи» и «+1д»,
в подтверждении и в уведомлении — тоже. Покрыто тестами
«Слот после полуночи…», «Игра не выходит за 02:00», «Ночная заявка сохраняет правильный игровой день».

Шаг сетки (`slotStepMinutes: 60`) и буфер уборки (`cleanupBufferMinutes: 15`) — операционные
константы в `src/config.js`. Границы смены меняются в админке («Настройки» → «Часы работы»)
и применяются к сетке слотов автоматически.

## 7. Атомарность и защита от двойной брони

`POST /api/bookings` выполняет проверку и вставку внутри одной транзакции
(`store.transaction`, глобальный мьютекс + откат в памяти при ошибке). Запись на диск —
через временный файл и `rename`, поэтому падение процесса не оставляет битый JSON.

Порядок проверок: валидация → существование и доступность сценария → сетка расписания →
границы смены → «не в прошлом» → **слот закрыт администратором** → **слот занят** → вставка.

Тест «Двойная бронь одного слота невозможна» отправляет два параллельных запроса и требует
ровно один `201` и один `409`.

### Anti-spam

* token bucket по IP (`RATE_LIMIT_MAX` за `RATE_LIMIT_WINDOW_MS`, по умолчанию 8 за 10 минут);
* honeypot-поле `website` — скрыто от людей, обязательно пустое;
* минимальное время заполнения формы (`FORM_MIN_FILL_SECONDS`);
* лимит размера тела запроса 64 КБ;
* отдельный, более строгий лимит на вход в админку (10 попыток за 15 минут).

### Audit log

`data/audit.log.jsonl` — append-only. Пишутся создание и отклонение заявки, смена статуса,
вход в админку (в том числе неудачный), правки контента, блокировка слотов, ошибки сервера.
Телефоны, имена, комментарии и e-mail **маскируются** (`••••4567`) — тест
«Audit log пишет и маскирует персональные данные» это проверяет.

## 8. SEO и доступность

* `<title>`, `description`, `canonical`, OG/Twitter, `sitemap.xml`, `robots.txt` — на сервере,
  из одного `SITE_URL`;
* JSON-LD: `LocalBusiness` + `EntertainmentBusiness`, `WebSite`, `BreadcrumbList`, `FAQPage`,
  `Review` (только подтверждённые), `Service`;
* локальные запросы в тексте без keyword stuffing: «квест Усть-Каменогорск», «страшный квест
  Усть-Каменогорск», «хоррор-квест с актёрами»;
* `/admin`, `/api/*`, `/booking/status` закрыты в `robots.txt`, а `/privacy` и
  `/booking/status` помечены `noindex`;
* доступность: skip-link, keyboard-навигация, видимый `:focus-visible`, `aria-live` для ошибок
  и успеха, `label` + `aria-required` + `aria-describedby` у всех полей, touch-target ≥ 44 px,
  `role="radiogroup"` с управлением стрелками для слотов, honeypot вне tab-порядка;
* при `prefers-reduced-motion: reduce` всё движение отключается;
* звук **выключен по умолчанию** и включается только явным кликом (эмбиент синтезируется
  через WebAudio — аудиофайлы не загружаются в critical path);
* lazy-load галереи, `width`/`height` для изображений, `poster` для видео — при добавлении
  реальных медиа; сейчас медиафайлов нет вовсе, поэтому критический путь минимален.

## 9. Приватность и право

* Согласие на обработку данных обязательно: без него `POST /api/bookings` возвращает `422`.
* Факт согласия фиксируется (`consentAt`) и хранится как доказательство законности обработки.
* Хранится минимум данных. Технический лог запросов не содержит тела заявок.
* `/privacy` — **черновик**. Перед публикацией его обязан проверить юрист на соответствие
  Закону РК «О персональных данных и их защите». Срок хранения (сейчас в тексте указан
  12 месяцев) должен подтвердить владелец.

## 11. Деплой на Vercel

Живые адреса: **https://fantom-quest.vercel.app** и **https://phantom-nine-delta.vercel.app**.
Проверено запросом: оба отдают один и тот же код этого репозитория. Внешний UX/CRO-аудит
выполнялся по второму адресу — см. `AUDIT.md`.

```bash
vercel link --scope bbc-b318 --project fantom-quest   # привязать папку к проекту
npm run deploy                                        # продакшн-сборка
npm run check:deploy -- https://phantom-nine-delta.vercel.app   # проверка стенда снаружи
```

### Как это работает

Vercel **нативно подхватывает `server.js`** как Node-сервер: он находит вызов
`server.listen()`, сам назначает внутренний порт и проксирует на него все запросы.
Переписывать приложение на serverless-функции не нужно — весь роутинг, серверный
рендер и API остаются теми же, что локально.

Три требования платформы, из-за которых приложение пришлось адаптировать:

1. **`module.exports` должен быть функцией или `http.Server`.** С обычным объектом
   Vercel отвечает `Invalid export found in module "server.cjs"` и отдаёт 500 на всё.
   Поэтому `server.js` экспортирует сам сервер, а `start`/`handle` навешаны на него
   свойствами.
2. **Нельзя вызывать `listen()` самому.** Порт назначает платформа; собственная
   привязка приводит к `ERR_SERVER_ALREADY_LISTEN` и запросы зависают без ответа.
   Локально порт по-прежнему выбираем мы (`if (!config.isVercel) listen()`).
3. **Статика должна попасть в бандл функции.** Она не раздаётся CDN-ом по умолчанию,
   поэтому в `vercel.json` указано `includeFiles` для `public/**` и `src/**`.

### Хранилище на Vercel

Файловая система на Vercel доступна только для чтения, а `/tmp` эфемерный: он живёт
внутри одного прогретого инстанса и исчезает вместе с ним. Поэтому файловый драйвер
там **не считается постоянным хранилищем**, и стенд автоматически переходит в
**демо-режим** (`demoMode`).

Что делает демо-режим:

| Поведение | Зачем |
|---|---|
| Заявка проходит весь путь и показывает обычный success-state | Публичный сценарий не отличается от рабочего — на страницах нет технических плашек |
| `MOCK_MODE` принудительно включается, даже если в переменных стоит `false` | Заявку нельзя ни подтвердить, ни отследить — значит, нельзя и уведомлять бизнес |
| `POST/PATCH/DELETE /api/admin/*` отвечают `503 demo_mode` | Изменения исчезли бы вместе с инстансом; честнее отказать, чем делать вид |
| Вход в админку и просмотр данных работают | Демонстрация панели не ломается |
| Режим виден только оператору: `/healthz` → `storage.demoMode`, `notifications.mockMode` | Техническое состояние — для владельца, не для посетителя |

### Как включить полноценную запись

Достаточно подключить к проекту Upstash Redis или Vercel KV — код менять не нужно.
Интеграция сама добавит переменные `KV_REST_API_URL` и `KV_REST_API_TOKEN`
(поддерживаются и имена Upstash: `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN`).

После этого драйвер становится `kv`, `demoMode` выключается, и:

* заявки сохраняются между запусками и видны в админке;
* атомарность держится **между инстансами**: перед каждой транзакцией берётся
  распределённая блокировка `SET NX PX` в Redis, а снимается скриптом
  compare-and-delete, чтобы не удалить чужую блокировку;
* уведомления администратору начинают уходить по-настоящему.

Проверить режим: `curl https://ваш-домен/healthz` → поле `storage`.

### Безопасность админки

Стандартный токен-заглушка `dev-admin-token-change-me` лежит в этом репозитории, то
есть известен всем. Поэтому на развёрнутом стенде (`VERCEL=1`) со стандартным токеном
**админка полностью закрыта**: и вход, и доступ по старой куке отвечают отказом
с объяснением, что нужно задать `ADMIN_TOKEN`.

Токен для текущего стенда лежит в `.admin-token.txt` (файл в `.gitignore`). Храните
его как пароль и меняйте при утечке: удалите переменную и добавьте заново.

## 12. Бэкап и откат

**Бэкап.** Все данные — один файл `data/db.json` плюс журнал `data/audit.log.jsonl`.

```bash
cp data/db.json "backups/db-$(date +%F-%H%M).json"
```

Простой ежедневный бэкап в cron:

```cron
0 4 * * * cd /srv/fantom && cp data/db.json backups/db-$(date +\%F).json && find backups -mtime +30 -delete
```

**Восстановление.** Остановить сервис, положить файл на место, запустить:

```bash
systemctl stop fantom
cp backups/db-2026-09-27.json data/db.json
systemctl start fantom
curl -s localhost:3000/healthz
```

**Откат кода.** `git checkout <предыдущий-тег> && systemctl restart fantom`.
Схема БД мигрирует вперёд автоматически (`store.migrate` добавляет отсутствующие коллекции),
поэтому откат кода на предыдущую версию с более новой базой безопасен: неизвестные поля
просто игнорируются.

**Если `db.json` повреждён**, сервер не упадёт молча: файл будет перемещён в
`db.json.corrupt.<timestamp>`, а в лог уйдёт понятная ошибка. Восстановите из бэкапа или
выполните `npm run seed` (это сотрёт заявки — сначала сохраните файл).

| Режимы стенда | постоянное хранилище vs демо; технические подробности не попадают в ответ пользователю; ни одна публичная страница при `demoMode: true` не содержит слов о режиме, хранилище и уведомлениях; админские изменения отклоняются с 503; вход и просмотр работают; `demoMode` принудительно включает `MOCK_MODE`; пустая переменная окружения не превращается в ноль; стандартный токен админки не пускает на развёрнутом стенде |

### Постоянное хранилище (драйвер kv)

`run.js` работает на файловом драйвере, поэтому kv — единственный путь к постоянному
хранилищу на Vercel — проверяется отдельно, `tests/kv-persistence.js`:

* поднимается заглушка Redis по REST-протоколу Upstash (без интернета и внешних сервисов);
* запускаются **два** процесса `server.js` с одной базой — как две лямбды на Vercel;
* заявка создаётся на первом и читается со второго;
* проверяется, что драйвер действительно берёт распределённую блокировку (`SET NX` + `EVAL`) —
  без неё два инстанса могли бы продать один слот дважды;
* проверяется, что база лежит в Redis, а не в памяти процесса.

Этот тест окупился сразу: он нашёл, что при общем хранилище чтение отдавало кэш своего
процесса. Заявку принимал один инстанс, а страница статуса и админка открывались на другом —
и не видели её. Теперь для драйвера с общим состоянием чтение всегда идёт в хранилище.

### Проверка в реальном браузере

`npm run qa:browser` — отдельный скрипт `tests/browser-qa.js`. `run.js` проверяет ответы API
и разметку, но он не нажимает кнопки; этот скрипт работает как посетитель. Он сам поднимает
сервер на временной базе, запускает системный Chrome через CDP и убирает за собой.

Что делает:

* обходит 10 маршрутов на 375 и 1440 px и на ширинах 320–430, проверяя переполнение, битые
  кадры, дубли `id`, число `H1`, `alt` у изображений, отсутствие технических подробностей
  и повторяющихся предложений в тексте;
* собирает ошибки консоли, ответы 4xx/5xx и обрывы загрузки за весь прогон;
* измеряет цели нажатия и проверяет, что элементы управления не меньше 44 px, а ссылки внутри
  текста — 24 px (у них по WCAG 2.5.8 другой порог и раздувать их нельзя);
* проверяет перекрытие элементов, предварительно прокручивая каждый в центр экрана: иначе
  липкая нижняя панель «перекрывает» то, что через мгновение окажется выше неё;
* проходит запись целиком на 375 px настоящими кликами и вводом и сверяет экран успеха
  с тем, что человек выбрал;
* проверяет крайние случаи: отсутствие согласия, короткий телефон, тройной клик по отправке,
  смену даты после выбора времени, отказ сети, перезагрузку посреди мастера;
* сверяет цену в карточке программы с ценой в сводке и минимальную цену с hero;
* измеряет CLS, LCP, вес критического пути и страницы целиком, а также что на телефоне
  грузится облегчённый кадр hero.

### Правила веб-интерфейса

Часть правил живёт в skill из [vercel-labs/agent-skills](https://github.com/vercel-labs/agent-skills)
(`web-design-guidelines`, он же набор `web-interface-guidelines`). Проверяются они скриптом
`tests/ui-rules.js` (`npm run qa:ui`) — на одной странице и за полминуты:

* у каждого интерактивного элемента есть доступное имя, у каждого поля — связанная подпись;
* переход табуляцией даёт видимый фокус, который ничем не перекрыт;
* страница сообщает браузеру `color-scheme: dark`;
* касание обрабатывается как `touch-action: manipulation`, подсветка касания задана вручную;
* заголовки используют `text-wrap: balance` — без висячего слова в последней строке.

Почему отдельным скриптом, а не частью `qa:browser`: длинная сессия с браузером в этом
окружении живёт на пределе — за десять минут обхода Chrome начинает падать, и результат
теряется. У `qa:browser` есть наборы проверок (`--blocks=core`, `--blocks=ui`), чтобы
укладываться в короткую сессию.

Отдельно стоит знать два ограничения замеров: локальный сервер отдаёт файлы без сжатия
(Vercel сжимает сам, для VPS сжатие настраивается на прокси), а `loading="lazy"` в headless
Chrome не откладывает кадры. Поэтому нормативы веса в скрипте — верхняя оценка, а не
PageSpeed-бюджет.

Дополнительно проверяется живой стенд снаружи:

```bash
npm run check:deploy -- https://fantom-quest.vercel.app
```

Отчёт заканчивается вердиктом: `ГОТОВ К ПРИЁМУ ЗАЯВОК` или `ДЕМО-СТЕНД` — с причинами и
ссылкой на ранбук `PRODUCTION.md`.

Проверки: страницы, статика, SEO (canonical, `og:image`, отсутствие `aggregateRating`
и `priceRange`), API, расчёт ночного слота, режим хранилища, полный путь заявки,
безопасность админки и — отдельно — отсутствие технических подробностей стенда в
публичном HTML (`/`, `/booking`, `/quests`, `/prices`).

### Скриншоты и замеры вёрстки

```bash
npm start                    # в одном окне
npm run shots                # в другом: полностраничные скриншоты + замеры переполнения
npm run shots:first-screen   # только первый экран — читаемый предпросмотр
```

Почему не `chrome --screenshot`: Chrome на Windows не даёт уменьшить окно ниже ~500 px, поэтому

Что он делает:

* проходит 11 страниц × 10 ширин (320, 360, 375, 390, 430, 768, 1024, 1280, 1440, 1920) —
  320 px проверяется отдельно: переполнение чаще всего находится именно там;
* измеряет `document.documentElement.scrollWidth` против `window.innerWidth` и перечисляет
  конкретные элементы, вылезающие за край;
* сохраняет полностраничные скриншоты (JPEG q82 — PNG такого размера весит в 6 раз больше);
* проходит мастер записи целиком на 390 px: без выбранной программы вперёд не пускает, после
  программы и даты переключается на шаги 2 и 3, без времени дальше не пускает, сводка совпадает
  с выбранным, sticky-summary не перекрывает ни одной кнопки активного шага;
* проверяет слой движения: сколько блоков осталось невидимыми после полной прокрутки, что
  нарисовано на canvas, реагируют ли фонарь и магнит на курсор, формат табло времени и что при
  `prefers-reduced-motion` видно всё без исключений;
* пишет `tests/artifacts/layout-report.md` и `layout-report.json`.

**Результат последнего прогона:** 100 замеров, горизонтальное переполнение — 0. Меню
раскрывается (`display: none → flex`, `aria-expanded=true`, 6 ссылок). Невидимых блоков после
полной прокрутки — 0 из 59. Canvas «чернил» рисует, фонарь и магнит реагируют на курсор, табло
времени в формате `ЧЧ:ММ:СС`. При `prefers-reduced-motion` скрытых блоков нет, фонарь

## 14. Миграция на PostgreSQL

Хранилище намеренно изолировано в `src/store.js` (методы `read`, `transaction`, `persist`).
При росте нагрузки или переходе на несколько инстансов:

1. Замените реализацию на пул `postgres` с теми же тремя методами.
2. Атомарность слота обеспечьте уникальным частичным индексом:

```sql
CREATE UNIQUE INDEX bookings_slot_active_unique
  ON bookings (business_date, start_time)
  WHERE status IN ('new', 'pending_confirmation', 'confirmed', 'moved');
```

3. Перенесите rate limit из памяти в Redis (интерфейс `ratelimit.check` уже это позволяет).

## 15. Дизайн

Визуальный язык — «городской подвал после полуночи»: почти чёрный графит, мокрый бетон,
тусклый грязно-зелёный и жёлтый свет, глубокий кроваво-красный **только** для опасности и CTA,
костяной текст, CCTV-таймкод, лёгкое зерно, следы изоленты. Атмосфера тревожная — интерфейс
спокойный и продающий: ни одна анимация не перекрывает CTA, ни один слот не создаёт
ложной срочности. Без дешёвого Halloween, фиолетовых неоновых градиентов, дыма и jumpscare.

Токены палитры и типографики — в начале `public/styles.css`.

### Слой движения

Движение вынесено во второй файл — `public/effects.css` + `public/effects.js`, а не размазано
по дизайн-системе. Причина практическая: `effects.css` можно отключить целиком, и сайт останется
читаемым и рабочим — он не задаёт ни сетку, ни типографику, только свет и переходы.

Концепция — «прямая трансляция из подвала»: посетитель смотрит на локацию через камеру.
Отсюда весь набор приёмов:

| Приём | Где | Что даёт |
|---|---|---|
| Визир — угловые скобки кадра | кадр hero, карточки программ, активный шаг записи, панель брони | кадр читается как картинка с камеры, а не как блок вёрстки |
| Луч по контуру | главные CTA, карточки программ при наведении | свет обегает рамку — акцент на действии, не на украшении |
| Фонарь за курсором | весь сайт, только мышь и только десктоп | одно пятно тёплого света, как от фонаря в подвале |
| Точечное табло | цифры в блоке «Проверяемые цифры» | числа набраны точками, как на старом табло |
| Поле «чернил» | под кадром hero, canvas 2D | медленное движение цвета в глубине кадра |
| Появление как переключение канала | заголовок каждой секции | секция «включается»: короткая потеря строки и резкий кадр |
| Магнит | главные кнопки | кнопка тянется к курсору, максимум 7 px |

Правила, которые слой обязан соблюдать и которые проверяет `npm run shots`:

* **без JS контент виден**: скрытое состояние включается классом `html.fx-on`, а не в базовом CSS;
* **`prefers-reduced-motion` выключает движение полностью** — вместе с canvas, фонарём и развёрткой;
* **экономный режим** (`Save-Data`, ≤ 2 ГБ памяти) оставляет только появление блоков;
* анимируются только `transform`, `opacity`, `filter`; поля и высоты не меняются, CLS = 0;
* canvas останавливается, когда кадр ушёл с экрана или вкладка неактивна;
* ни один слой не перекрывает CTA, меню и текст: у всех декоративных элементов
  `pointer-events: none` и `aria-hidden`.
